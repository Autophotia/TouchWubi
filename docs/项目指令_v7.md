## 3. 标准工作流程（七阶段）

### 阶段一：问题反馈（Bug 结构化）

用户报告问题（"打不出某字"、"联想不对"、"某个命令没反应"等）时，先整理成标准 Bug 描述，**缺失字段主动追问**：

- **环境**：设备型号、系统版本、App 版本、使用的方案（ly_wubi / ly_wubi_14 / ly_wubi_pinyin / ly_wubi_pinyin_14）与主题
- **版本基线**：对应 BASELINE.md 版本；最近的改动（`git log`）
- **复现信息**：前置条件、复现步骤（具体到按键序列，如"输入 `abcd` 后按 `;`"）、实际结果、期望结果
- **证据**：截图、`log/keyboard`、`log/app`、assoc_probe.log 日志片段
- **影响范围**：单方案 / 双端 / 是否阻断日常使用；严重程度、优先级、是否阻断发版
- 提醒用户：可将 Bug 创建为项目事项并分配，关联原需求 / PRD / 测试用例

### 阶段二：证据定位

- **一切结论基于证据**：先读日志再谈原因，**不在证据不足时断言根因**；对代码 / 日志 / 接口问题的判断必须标注依据
- 排查路径：复现 → 看 `log/keyboard` 与 `log/app` 有无新 error → 定位到具体 lua / schema → 对照 BASELINE.md 确认是否已知限制

  - schedule.lua：**已证实正常工作**（`generate_candidates` 定义在 `lua/lib/lunar.lua`，随包分发），"一用必崩"是早期静态分析误判，已推翻

9. 输入统计：`/qk` 清空后正常编码上屏计入、点联想词不计入、复制/语音不计入、空格/分号/引号快捷上屏计入、极速无爆涨（几百字/分）

回归结果结构化记录：原问题是否解决 / 相关功能是否受影响 / 边界场景是否覆盖 / 遗留问题与风险点。提醒用户：可将回归结果更新到 Bug 事项中，并通知验收。

## 7. 资料上云与协作分工（方案 C，2026-10-24 确立）

1. **两个云，各司其职**：
   - **git（GitHub TouchWubi）＝ 版本库**：管「演进」。存放代码 + 设计文档 + 基线 + 项目指令。有版本历史、diff、合并、评审。
   - **腾讯云（tdrive / 资产库）＝ 共享文件系统**：管「分发」。存放打包产物、补丁 zip、报告。上传即覆盖，无版本历史。
2. **设计基线统一进 git 的 `docs/`**（仓库根 `schemas/TouchWB/docs/`）：
   - `BASELINE.md`（项目基线）、设计文档（如 联想库导入导出设计.md）、项目指令（v7 及以后）。
   - 这是「参与设计」的**权威源（source of truth）**：同账号不同电脑靠 `git pull` 拿最新设计；成员靠 git 协作（push / PR / 评审）。
   - ⚠ **旧约定「BASELINE.md 不进 git」废止**：改为放 `docs/` 隔离（不混在代码目录里），随代码一起 push。
3. **产物分发走腾讯云 tdrive**：release zip、补丁 zip、报告等成品放 tdrive `/02-产物/`，供所有人下载 / 浏览；资料类 `/01-资料/`、笔记 `/03-笔记/`。
4. **临时讨论 / 想法征集走项目动态 + 任务**，不落文件。
5. **项目记忆 `.workbuddy/memory` 保持本地**：不进 git、不上云——它是 agent 的工作日志（附当日事实与结论），非协作资料，只在本机供 agent 续接上下文。
6. **成员参与设计的两条路径**：
   - **会 git 的成员**：直接给 GitHub 仓库 push 权限，设计文档在 `docs/` 里协作（diff / 评审 / 合并）。
   - **不会 git 的成员**（产品 / 测试等非技术角色）：在项目动态 / 任务里提想法，由维护者落到 git `docs/`；定稿后把可读副本传一份到 tdrive 供浏览，**权威版本始终在 git**。
7. **权威层级**：git `docs/`（权威源）> tdrive 副本（仅供浏览）> 项目记忆（本地）。
