## 四、第 3 项的技术依据（本次核心发现）

### librime 源码（1.8.0 / 1.17.0 / master 三份 `src/rime/gear/speller.cc` 一致）

```cpp

  }
  ...
}
```

```cpp
// handles input beyond max_code_length when auto_select is false.
if (is_initial && AutoSelectAtMaxCodeLength(ctx)) { ... }

bool Speller::AutoSelectAtMaxCodeLength(Context* ctx) {
  // 不依赖 auto_select_；检查「已有候选」是否达到 max_code_length
  if (cand && reached_max_code_length(cand, max_code_length_) &&
      is_auto_selectable(cand, ctx->input(), delimiters_)) {
```

### 推论

1. **第 5 码顶首 ✔**：`max_code_length: 4` + `auto_clear: max_length`，4 码后再按键触发 `AutoSelectAtMaxCodeLength` → `ConfirmCurrentSelection()` 确认首候选，第 5 码成为下一字首码。4 码重码时第 2/3 候选在 4 码阶段仍可选 ✔（对应需求 3 末条、需求 4）。
2. **2/3/4 码唯一自动上屏 ❌（标准 librime 下）**：fixed 保留 `auto_select: false`，`AutoSelectUniqueCandidate` 首行即返回；`auto_select_unique_candidate: true` 不是被引擎读取的配置项。
3. 即便把 `auto_select` 改成 `true`，因 `auto_select_pattern` 已删且 `max_code_length: 4`，只有**码长 ≥4 的唯一候选**会触发，2/3 码仍不会；且 `translator/enable_completion: true`（`ly_wubi.schema.yaml:286`）会带补全候选，`Prepare(2)==1` 的唯一判定更难成立。

### App 侧不确定性（不能断言，需真机验证）

- 日志 `Rime version: 1.17.0`；App 补丁库 `dev/space/patches/code_unique_auto_select/patch.yaml` 把 `auto_select` 与 `auto_select_unique_candidate` 作为**配套开关**（两者默认均 `true`），`patch_to: "{$current_schema}"`。
- 若 App 的 librime 是定制版并单独实现了该 key，第 3 项可能成立 ⇒ **定性为「存疑」而非「确定不满足」**。但该补丁同时把 `auto_select` 设为 true，fixed 没有这一点，倾向不生效。
- 该补丁 master switch 默认 `false`；若用户开了它，会 patch 到当前方案并覆盖 speller，是验收时的干扰变量。

**最小修法（本次不执行）**：`auto_select: true` + 一条覆盖 2~4 码的 `auto_select_pattern`（如 `^[a-z]{2,4}$`），或确认 App 补丁行为后再定；改前须评估对「4 码重码保留候选」的影响（`Prepare(2)==1` 保证重码不触发，逻辑上安全）。

### ③ 的源码级定性（librime 1.17.0 `src/rime/gear/speller.cc`，与 App 所用版本一致）

```cpp
// 按键前
if (is_initial && AutoSelectAtMaxCodeLength(ctx)) { ... }
else if ((auto_clear_ == kClearMaxLength || auto_clear_ == kClearManual) && AutoClear(ctx)) { ... }
ctx->PushInput(ch); ctx->BeginEditing();
if (AutoSelectPreviousMatch(...)) { ... }
if (AutoSelectUniqueCandidate(ctx)) { ... }
else if (auto_clear_ == kClearAuto && AutoClear(ctx)) { ... }

bool AutoSelectAtMaxCodeLength(Context* ctx) {
  if (max_code_length_ <= 0) return false;
  if (!ctx->HasMenu()) return false;              // ← 无候选直接放弃
  auto cand = ctx->GetSelectedCandidate();
  if (cand && reached_max_code_length(cand, max_code_length_) && is_auto_selectable(...)) {
    ctx->ConfirmCurrentSelection(); return true;
  }
  return false;
}
bool AutoClear(Context* ctx) {
  if (!ctx->HasMenu() && auto_clear_ > kClearNone &&
      (auto_clear_ != kClearMaxLength || max_code_length_ == 0 ||
       ctx->input().length() >= (size_t)max_code_length_)) {
    ctx->Clear(); return true;
  }
  return false;
}
```

- **`max_code_length` 本身不截断输入**，只用于两处：顶首判定（`AutoSelectAtMaxCodeLength`）与 `AutoClear` 的长度门槛。空码时 `HasMenu()` 为 false ⇒ 顶首不成立、唯一候选判定也不成立 ⇒ 每按一键都 `PushInput` 追加，5/6/7… 码长串一直挂着；`auto_select_pattern` 只匹配 4 码，5 码以后永不自动上屏，直到手动 Esc / 退格。
- **唯一能截断空码串的是 `auto_clear`**，而上游三个取值都无法同时保住 A5：

| 取值 | 触发时机 | 门槛 | 对 A5 的影响 |
|---|---|---|---|
| `max_length` | 按键前 | `!HasMenu() && input().length() >= 4` | `ctx->input()` **含尚未 commit 的已选段**，顶首「中国」后累计长度已 ≥4；拼音反查链路上只要出现无候选状态（单 `z` 或某个组合），下一次按键前就 `Clear()` 整串 ⇒ 编码栏清空、反查中断 |
| `manual` | 按键前 | 无长度门槛（`!= kClearMaxLength` 使括号恒真） | 任何无候选状态都清空：2/3 码空码提前清空 + 同样打断反查，代价更大 |
| `auto` | 按键后 | 无长度门槛 | `PushInput` 后只要无候选立即清空，空码 4 码刚打完就清、A5 直接失效 |

> 由此也修正此前日志里「`auto_clear` 把刚 PushInput 的第 5 码当作超长清掉」的描述：实际是**按键前**检查、`Clear()` 清空整串，判据是累计 `input().length() >= 4` 且当前无候选。结论（它是 A5 元凶、必须删）不变。

### 处置建议

1. **推荐：保持现状，登记为已知取舍**。③ 只在「4 码空码后仍继续盲打」时出现，按 Esc / 退格即可恢复；换来的是 A5（顶首后拼音反查）这一高频链路正常。
2. 若必须两全，唯一干净路径是 **26 键专属 lua processor**：条件限定「当前未确认段长度 ≥4 且该段无候选」，只清当前段，不碰顶首后残留的 `z` 段（长度 1）与有候选的反查段。代价：新增 lua、挂载 processor（引擎顺序红线）、再验一轮。

## 九、补充：Rime 原生机制能否实现「微软五笔」式空码处理（11-10 追加）

> ⚠️ 本节「本项目不能直接加回 `auto_clear`」的推断同样已被 §十一 推翻；但「Rime 能实现微软式空码处理，机制是 `auto_clear: max_length`」这一判断是对的，保留。

### 用户给出的对照

- **微软五笔**：4 码无候选声音报警；继续打第 5 码 → 清空编码栏，第 5 码成为下一输入首码。
- **小艺五笔**：4 码无候选后编码栏残留长串（与本 fixed 现状相同）。
- **百度输入法**：网络词覆盖面极广，任意编码几乎都有词组，很难出现空码。

### 结论：**能，而且就是被删掉的 `auto_clear: max_length`**

`AutoClear()` 在**按键前** `ctx->Clear()`，随后 `ProcessKeyEvent` 无条件 `ctx->PushInput(ch)` ⇒ 空码 4 码后按第 5 码，整串清空、第 5 码成为新段首码，**与微软五笔一致**。它是 schema 配置项，不是引擎内建的「五笔默认机制」。

- 官方 `rime/rime-wubi` 的 `wubi86.schema.yaml` 的 speller 段只有 `delimiter: " ;'"`，`#max_code_length: 4` 是注释掉的，**完全没有** `auto_clear` / `auto_select`；z 反查靠 `recognizer` 的 `reverse_lookup: "^z[a-z]*'?$"` + `reverse_lookup_translator`。⇒ 社区五笔方案常见的「`max_code_length` + `auto_select` + `auto_select_pattern` + `auto_clear: max_length`」四件套不是 Rime 默认，官方方案反而不用；Rime 只是引擎，五笔行为由各方案自己配。
- 「无候选报警」Rime 引擎**无原生实现**（引擎无声音 API），只能由 App 侧或自定义组件做。
- 「打满 4 码立即清空」（不等第 5 码）对应 `auto_clear: auto`（按键后 `AutoClear`），代价是刚打的第 4 码一并清掉、A5 直接失效。

### 本项目为何不能直接加回（源码判据）

`AutoClear` 判据是 `!HasMenu() && input().length() >= 4`。librime 1.17.0 `context.cc` 实证：

```cpp
bool Context::ConfirmCurrentSelection() {
  Segment& seg(composition_.back());
  seg.status = Segment::kSelected;   // ← 只打标记，不 commit、不清 input_
  ...
}
bool Context::Commit() {
  if (!IsComposing()) return false;
  commit_notifier_(this);
  Clear();                            // ← 只有 Commit() 才清空 input_ / composition_
  return true;
}
```

⇒ 在 speller 处理期间，顶首产生的已选段尚未 commit，`ctx->input()` 仍累计（"khlg" + 后续），长度已 ≥4；z 拼音反查链路上任一「无候选瞬间」都会在按键前 `Clear()` 整串 ⇒ A5 失效。`auto_clear` 三个取值（§八表）都无法把判据限定为「**当前段**长度 ≥4 且无候选」。
